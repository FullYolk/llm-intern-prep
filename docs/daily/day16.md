## Embedding(向量化)
* Embedding在本质上是一种将离散的符号（文本、图像等）映射到连续的、低维且稠密的向量空间的技术。在 Embedding 构造的高维空间中，语义相近的文本，其向量的几何距离（通常用余弦相似度衡量）会非常接近，这就使得机器具备了计算语义相似度的能力。
* 在 RAG 架构中，Embedding 过程主要分为离线和在线两步：
离线建库阶段：文档经过清洗、Chunking 后，会被送入 Embedding 模型（如 BGE、OpenAI text-embedding-3 等），转换为向量，连同原始文本及其 Metadata（如来源、页码）一起存入向量数据库（如 Chroma、FAISS）。
在线检索阶段：用户的 Query（查询词）也会经过同一个 Embedding 模型转换为向量，然后在向量数据库中执行 ANN（近似最近邻）搜索，召回 Top-K 个最相关的 Chunk。”
* 难点：维度诅咒与细节丢失：把一个长达 500 字的 Chunk 强行压缩成 1024 维的向量，必然会丢失细节。尤其是专有名词、产品型号、工单号这种极度依赖字面匹配的词汇，Embedding 往往捕捉不到。
跨语言与多模态对齐：如果用户用英文提问，文档是中文的，很多早期的模型在同一语义下的跨语言向量距离很远，导致检索失败（现在大多通过 M3 这种多语言模型解决）。
不对称检索问题：用户的 Query 通常只有几个字（如‘请假制度’），而库里的 Chunk 是大段文字，两者的文本长度和结构严重不对称，直接算距离效果可能不佳（这引出了我们后续做 Query Rewrite 或 HyDE 优化的需求）。”
* 在 LangChain 框架里，所有的 Embedding 工具类都必须遵守一个“接口协议”，必须实现两个核心方法：
embed_query(text: str)：用来转换用户的搜索词（单条）。
embed_documents(texts: List[str])：用来转换文档库里的 Chunks（批量）。
本质就是一个带POST请求的适配器，也是LangChain封装的底层逻辑
* Embedding目前使用的算法，全都是基于 Transformer 架构 + 对比学习 (Contrastive Learning)。：
* ：

Token 化与自注意力 (Self-Attention)：
当你输入“苹果手机真好用”，模型会把它切成 token。在 Transformer 内部，每一个字都会去“审视”其他字（比如“苹”会发现自己和“果”、“手机”绑在一起）。通过这种多层审视，模型理解了这里的“苹果”是指数码产品，而不是一种水果。

降维池化 (Pooling)：
Transformer 算完后，每个 token 都会变成一个向量。但我们需要代表整句话的向量。算法通常会提取一个特殊的 [CLS] 标记的向量，或者把所有 token 的向量取平均（Mean Pooling）。这就是你最终看到的那个 1024 维度的数字串。

它是怎么被训练出来的？（对比学习）：
在训练的时候，工程师会给模型输入三句话：

A（原句）：“苹果手机真好用”
B（正例，意思相近）：“iPhone的体验很棒”
C（负例，意思相反或无关）：“我今天吃了一个香蕉” 算法的目标就是：在数学空间里，死命把 A 和 B 的距离拉近，把 A 和 C 的距离推远！（这就是对比学习的本质）。
经过海量数据的“拉近推远”训练，模型就具备了分辨语义相似度的能力。
* 向量库：
* 传统的 MySQL 用的数据结构是 B+ 树，用来做精确查找（比如 id=5）。
而 Vector Store（向量库）用的核心数据结构通常是 HNSW (分层可导航小世界图)。当你拿着查询词的向量放进去时，它顺着网格一层一层往下找，谁离它近，它就往谁走。这种算法叫做 ANN (Approximate Nearest Neighbor, 近似最近邻搜索)。
* 在实际生产中 会链接专业的向量数据库。
* 关于调优：向量与 Metadata 的分离存储： 向量库底层其实是两张表。一张表存 1024 维的数字（用来做数学距离计算），另一张表存 Metadata（比如来源是 fastapi_notes.md）。搜索时，先通过向量算距离，然后再把关联的原文和来源拉出来。
批处理 (Batching) 与 限流 (Rate Limit)： 如果我们有一本 10 万字的书，切出了 2000 个 chunk，直接 Chroma.from_documents 会报错！因为第三方 API 通常限制“每分钟最多请求 1000 次”或“每次最多 50 个”。高级开发者需要自己写循环，分批次（Batch）发送，并加上 time.sleep() 或指数退避重试机制。
维度的兼容性： 不同模型产生的向量维度是不一样的（比如 OpenAI 是 1536 维，智谱是 2048 或 1024 维，BGE 是 1024 维）。如果你一开始用 BGE 建了库，后来老板让你换 OpenAI 的模型，程序会直接崩溃，因为 1024 维的尺子量不了 1536 维的向量。你必须清空旧库，重新计算所有文档！
* 相似度的度量：不同的数据库默认返回值不同。通常有三种度量方式：

Cosine Similarity (余弦相似度)：最常用。衡量两个向量在空间中的夹角。夹角越小，语义越近。（不受文本长短影响，大模型最爱）。
L2 Distance (欧几里得距离/L2范数)：衡量两点之间的直线绝对距离。** ChromaDB 默认使用的是 L2 距离，所以返回的 score 越小，表示距离越近，相关性越强。**
Inner Product (内积)：如果向量做过归一化，内积和余弦相似度等价，但计算更快。
* K topk召回：k 设置太小，容易漏掉关键信息（低召回率）； k 设置太大，几万字的片段全塞给大模型，会导致模型“注意力涣散”（大海捞针失败），而且会消耗巨额的 Token 费用（每次提问多花几毛钱）。
* 其他搜索方式：MMR搜索（最大边际相关性）：在保证“相关性”的同时，强行增加“多样性”。 
* 实际生产中RAG优化还需要：混合检索 重排 查询重写
