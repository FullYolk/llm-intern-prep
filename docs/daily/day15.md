## RAG文件加载
* 常规场景可以直接读入内存
* 海量工业场景不能使用 必须使用lazy loading/生成器：
def lazy_load_docs(data_dir):
    for path in Path(data_dir).glob("*.md"):
        text = path.read_text()
        # 不是放进 list 里，而是读一个交出去一个
        yield Document(page_content=text, metadata={"source": str(path)})

## chunk切分
* 切分太碎真正带来的“工程灾难”是：
Embedding 成本飙升： 我们要把文本变成向量，往往需要调用收费的 Embedding API（比如 OpenAI 的接口）。切出 84 个块就要调 84 次，切出 8 个块只要调 8 次，这是实打实的烧钱。
向量数据库检索变慢： 向量数据库在做检索时，要计算你提出的问题和库里每一个 Chunk 的数学距离。Chunk 数量翻了 10 倍，数据库的计算压力和耗时也会成倍增加。
* 同时算法层面会导致严重的语义碎片化 大模型缺乏完整的上下文无法理解 容易产生幻觉
* 在真实的工业生产中，如果我们真的需要小 chunk 带来的‘精准定位关键词’的能力，我们一般不会单独使用它，而是会采用 Parent-Child Retriever（父子块检索） 的高级架构：用 50 字的小块去做精准检索，命中之后，不把小块给大模型，而是把它所属的 500 字的大块（父块）取出来交给大模型。这样既保证了检索精度，又保留了完整的语义。”
* chunk太大：检索不精准

## 算法
* 二叉树的直径：套皮的深度 维护一个全局变量记录最大值
* 对称二叉树：自下而上递归 判断左左==右右且左右==右左
* 有序数字转化为二叉搜索树：左右指针 分治+递归建树
